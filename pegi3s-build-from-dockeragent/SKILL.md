# When to use this skill

Load this skill when dockeragent has generated a submission directory such as:

```text
.../dockeragent_results/<tool>/for_submission/
├── Dockerfile
├── License
├── README.md
├── metadata.json
├── ontology.diaf
└── test_data/
    ├── input_test_data/
    └── output_test_data/
```

The goal is to turn that output into a complete, reproducible image entry in
`pegi3s/dockerfiles`, including the image files, metadata, ontology mappings,
uploaded test data, and a passing `bdip` auto-test.

# 1. Inspect the generated submission

1. Identify the tool name, version, and upstream GitHub repository.
2. Verify that the version exists upstream:
   - Check the GitHub release/tag.
   - For a tag, `git ls-remote --tags <repo>` must list it.
3. Inspect the generated `Dockerfile`:
   - It MUST pin the upstream version. If it clones `master`/`main` or uses an
     unpinned URL, change it to a fixed tag or source release.
   - Prefer:
     ```dockerfile
     git clone --branch "v${VERSION}" --depth 1 <repo_url> /opt/<tool>
     ```
   - `git clone --branch` accepts tags as well as branches. A tag produces a
     detached HEAD at the tagged commit, which is exactly what is wanted.
   - Alternatively, download the source archive for the exact tag/release.
   - Never download pre-compiled release binaries.
4. Check that the base image is pinned (e.g. `ubuntu:24.04`, never `:latest`).
5. Check that build dependencies are removed from the final image where
   practical.
6. Inspect `README.md`, `License`, `metadata.json`, `ontology.diaf`, and the
   test data.

# 2. Choose the image layout

Use the repository conventions:

- Parametrized image with `ARG VERSION`:
  ```text
  <tool>/<major>.x/
  ├── Dockerfile
  ├── README.md
  ├── License
  └── BUILD.md
  ```
  Examples: `raxml/8.x`, `iqtree3/3.x`, `hyphy/2.x`.

- Fixed single-version image:
  ```text
  <tool>/<version>/
  ```
  or, when the repository uses root-level images:
  ```text
  <tool>/
  ```

For new images, prefer the parametrized layout when the upstream project
publishes version tags.

# 3. Create the image files

## Dockerfile

- Keep the Apache 2.0 copyright header.
- Use `ARG VERSION`.
- Pin the source to `v${VERSION}`.
- Build from source with the documented build system.
- Remove temporary source and build dependencies.
- Set `WORKDIR /data`.

Example:

```dockerfile
FROM ubuntu:24.04

ARG VERSION

RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential \
        autoconf \
        automake \
        pkg-config \
        git \
        ca-certificates \
    && git clone --branch "v${VERSION}" --depth 1 \
       https://github.com/<owner>/<repo> /opt/<tool> \
    && cd /opt/<tool> \
    && ./configure --disable-native \
    && make -j"$(nproc)" \
    && cp src/<tool> /usr/local/bin/<tool> \
    && cd / \
    && rm -rf /opt/<tool> \
    && apt-get purge -y --auto-remove build-essential autoconf automake pkg-config git \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /data
```

## README.md

Include:

1. The standard project header.
2. A short description of the tool.
3. A Linux usage command.
4. Explanations of the placeholders.
5. The output files produced by the tool.
6. The help command.
7. A link to the uploaded test data ZIP.

## License

Copy the generated `License` file. Recent images use the filename `License`
with a capital `L`.

## BUILD.md

For parametrized images, add:

````markdown
# Building instructions

Specify the <tool> version in `<tool>_version` and run (from this directory):

```bash
<tool>_version=<version> && docker build ./ -t pegi3s/<tool>:${<tool>_version} --build-arg VERSION=${<tool>_version} && docker tag pegi3s/<tool>:${<tool>_version} pegi3s/<tool>:latest
```

# Notes

<Brief build notes.>

# Build log

- <version> - DD/MM/YYYY - <author>
````

# 4. Build and verify the image

Run from the image directory:

```bash
cd <image_dir>
<tool>_version=<version>
docker build ./ -t pegi3s/<tool>:${<tool>_version} --build-arg VERSION=${<tool>_version}
docker tag pegi3s/<tool>:${<tool>_version} pegi3s/<tool>:latest
```

Verify the image reports the expected version:

```bash
docker run --rm pegi3s/<tool>:${<tool>_version} <tool> --version
```

If the tool has no `--version` flag, run its help command and check the version
banner.

Run a small manual analysis when possible and confirm that the expected output
files are created.

# 5. Prepare and upload test data

## Important BDIP path semantics

When `auto_tests[0].input_files` contains a URL to a ZIP:

1. BDIP downloads it to `<cache>/<image_name>/<zip_name>`.
2. BDIP extracts it into `<cache>/<image_name>/`.
3. The cache is mounted at `/data/input_data`.

Therefore:

- The input ZIP must contain the input files **at its root**.
- It must NOT contain a top-level `<image_name>/` folder, otherwise the files
  end up at `/data/input_data/<image_name>/<image_name>/...`.
- The auto-test command must reference files as
  `/data/input_data/<image_name>/<file>`.

## Input data

Create the ZIP manually so it is named exactly `<tool>.zip` and contains the
input files at the root:

```bash
mkdir -p /tmp/opencode/<tool>_input
cp <input_file> /tmp/opencode/<tool>_input/
cd /tmp/opencode/<tool>_input
zip -j /tmp/opencode/<tool>.zip <input_file>
```

Verify:

```bash
unzip -l /tmp/opencode/<tool>.zip
```

Upload:

```bash
source /home/hlfernandez/miniconda3/etc/profile.d/conda.sh
conda activate bdip-tools
bdip upload-test-data /tmp/opencode/<tool>.zip test_data
```

`bdip upload-test-data` does not re-zip a file in `test_data` mode, so the
remote file is uploaded as `<tool>.zip`.

## Output data

The output ZIP must contain a top-level `<tool>_output/` folder:

```text
<tool>_output/
├── <output_file>
└── ...
```

Create the directory from the generated output ZIP:

```bash
mkdir -p /tmp/opencode/<tool>_output
unzip -j <generated_output.zip> -d /tmp/opencode/<tool>_output
```

Upload the **directory**, not the existing ZIP:

```bash
bdip upload-test-data /tmp/opencode/<tool>_output test_results
```

In `test_results` mode, `bdip` always zips. Passing a directory produces
`<tool>_output.zip` with the correct top-level folder. Passing an existing ZIP
would create a ZIP inside a ZIP.

## Verify the uploads

```bash
curl -sIL http://evolution6.i3s.up.pt/static/pegi3s/dockerfiles/input_test_data/<tool>.zip
curl -sIL http://evolution6.i3s.up.pt/static/pegi3s/dockerfiles/output_test_data/<tool>_output.zip
```

Both must return HTTP 200. Download and inspect the ZIPs if necessary.

# 6. Update `metadata/metadata.json`

Append a new object to the metadata array, preserving the existing formatting:

- top-level array items use two spaces;
- object keys use four spaces;
- literal UTF-8 characters;
- trailing newline at the end of the file.

Use the generated `metadata.json` as the starting point, but fix:

1. `manual_url`: must be a non-empty upstream documentation URL.
2. `test_data_url`: URL to the input `<tool>.zip`.
3. `test_results_url`: URL to the output `<tool>_output.zip`.
4. `auto_tests[0].input_files`: full URL to the input `<tool>.zip`.
5. `auto_tests[0].commands`: use the correct
   `/data/input_data/<image_name>/...` path and write to
   `/data/output_folder/<output_dir>/<output_file>`.
6. `recommended[0].date`: date of the successful test in `DD/MM/YYYY`.
7. `comments`: mention output files and help command.
8. `status`: `Usable` only after the test passes.

Template:

```json
{
  "name": "<tool>",
  "description": "<short description>",
  "project_active": true,
  "status": "Usable",
  "recommended": [
    {
      "version": "<version>",
      "date": "DD/MM/YYYY"
    }
  ],
  "latest": "<version>",
  "bug_found": [],
  "not_working": [],
  "no_longer_tested": [],
  "manual_url": "https://...",
  "source_url": "https://github.com/...",
  "comments": [
    "<output file note>",
    "To see the help, run: docker run --rm pegi3s/<tool> <tool> -h."
  ],
  "gui": false,
  "gui_command": "",
  "podman": "untested",
  "singularity": "untested",
  "invocation_general": "docker run --rm -v /your/data/dir:/data pegi3s/<tool>",
  "usual_invocation_specific": "<example command>",
  "usual_invocation_specific_comments": [
    "<placeholder explanations>"
  ],
  "test_invocation_specific": "<manual test command>",
  "test_data_url": "http://evolution6.i3s.up.pt/static/pegi3s/dockerfiles/input_test_data/<tool>.zip",
  "test_results_url": "http://evolution6.i3s.up.pt/static/pegi3s/dockerfiles/output_test_data/<tool>_output.zip",
  "icon": "",
  "input_data_type": [
    "<type>"
  ],
  "auto_tests": [
    {
      "docker_image": "pegi3s/<tool>:<version>",
      "input_files": [
        "http://evolution6.i3s.up.pt/static/pegi3s/dockerfiles/input_test_data/<tool>.zip"
      ],
      "output_dir": "<tool>_output",
      "output_file": "<output_file>",
      "add_config": "",
      "commands": "<command that creates the output file>"
    }
  ],
  "custom_searches": {
    "pubmed": "term=<tool>",
    "scholar": "q=<tool>",
    "bioprotocol": "content=<tool>",
    "bioprotocol_exchange": "content=<tool>"
  }
}
```

Validate:

```bash
python3 -m json.tool metadata/metadata.json > /dev/null
bdip check-metadata-json
```

Also check the new entry does not have missing required fields:

```bash
bdip check-missing-field manual_url
bdip check-missing-field test_data_url
bdip check-missing-field test_results_url
bdip check-missing-field source_url
```

Filter the output for the new tool name.

# 7. Update `metadata/dio.diaf`

The generated `ontology.diaf` contains DIO term IDs, but `dio.diaf` requires
`DIO:ID<TAB>program_name`.

1. Confirm each term exists and is a leaf term in `metadata/dio.obo`.
2. Add the mappings:

```bash
bdip ontology-edit-diaf add \
  --line $'DIO:0000540\t<tool>' \
  --line $'DIO:0000547\t<tool>'
```

Use the actual DIO IDs from the generated `ontology.diaf`.

3. Validate:

```bash
bdip check-diaf
```

# 8. Run the automated test

Always use `--dry-run`. Running `bdip test-images` without `--dry-run`
rewrites the entire metadata file with Python `json.dump` defaults and creates
a large unintended diff.

```bash
source /home/hlfernandez/miniconda3/etc/profile.d/conda.sh
conda activate bdip-tools
bdip test-images --image <tool> --skip-pull --dry-run --force-download-inputs
```

Notes:

- `--skip-pull` uses the image just built locally.
- `--force-download-inputs` avoids stale cached test data.
- `bdip test-images` currently uses only `auto_tests[0]`.
- The test succeeds only if `output_file` exists and is non-empty.

If the test fails:

1. Inspect the command output.
2. Check the input path inside the container.
3. Check the output file name.
4. Check that the image tag matches `auto_tests[0].docker_image`.
5. Fix and repeat.

# 9. Final checks

Run:

```bash
bdip check-diaf
bdip check-metadata-json
bdip check-missing-field manual_url
bdip check-missing-field test_data_url
bdip check-missing-field test_results_url
bdip hadolint --path <image_dir>/Dockerfile
git diff --check
git status --short
```

Confirm:

- `recommended[0].date` is the successful test date.
- `latest` matches the image version.
- `auto_tests[0].docker_image` uses the versioned tag.
- `test_data_url`, `test_results_url`, and `input_files` point to the uploaded
  ZIPs.
- The input ZIP contains files at the root.
- The output ZIP contains `<tool>_output/`.
- The Dockerfile is pinned to a fixed version.
- `metadata/dio.diaf` has the new mappings.
- No temporary or untracked inspection artifacts remain (e.g.
  `data_downloads/`).

# 10. Commit, push, and publish

Only do this when explicitly requested:

1. Commit the new image folder and metadata changes.
2. Push the image:
   ```bash
   docker push pegi3s/<tool>:<version>
   docker push pegi3s/<tool>:latest
   ```
3. Update Docker Hub documentation if the project workflow requires it.

# Common pitfalls

- Dockerfile clones `master`/`main`: fix it to a tag or source release.
- Input ZIP contains a top-level `<tool>/` folder: BDIP will extract it to
  `/data/input_data/<tool>/<tool>/...`.
- Uploading an existing output ZIP in `test_results` mode creates a nested ZIP;
  pass the output directory instead.
- Running `bdip test-images` without `--dry-run` rewrites metadata.
- `manual_url` or `test_results_url` left empty.
- `auto_tests[0].commands` using `/data/input_data/<file>` instead of
  `/data/input_data/<image_name>/<file>`.
- Output file name in `commands` does not match `output_file`.
- Version in `latest`, `recommended`, and `auto_tests[].docker_image` differs.
- Using an ontology term that is not a leaf term in `dio.obo`.
- `bdip upload-test-data` skips files that already exist on the server. Check
  before re-uploading.
- `git clone --branch <tag>` is valid for tags; the result is a detached HEAD,
  which is expected.
- If a source archive download fails with `wget` exit code 4, use the pinned
  `git clone --branch <tag>` form instead.
- `bdip check-metadata-json --enforce-schema` currently reports pre-existing
  issues in other entries (`gui_command`, empty `auto_tests` fields). Use the
  normal `bdip check-metadata-json` check unless schema enforcement is
  explicitly required.
